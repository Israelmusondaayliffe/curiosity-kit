# Research and customers

Use this method for recent commercial signals, an ICP hypothesis, first-customer discovery, a prospect report or a bounded competitor/hiring question. It works from supplied evidence when live research is unavailable or unnecessary. Read [evidence and review](../references/evidence-and-review.md) before qualification.

## Frame the search so it can reject weak matches

Identify product/outcome, primary user, economic buyer, urgent job, current alternative, adoption trigger, geography/language, constraints and disqualifiers. A URL may explain the advertised offer but not prove delivery, demand or customer results. Label interpretation. When the offer is undecided, return the material choice or use [discovery and offer](discovery-and-offer.md), rather than collecting an indiscriminate lead list.

Select an explicit date interval and as-of date for a recent request. Do not silently use “last 30 days” for every task or describe older results as current. Preserve publication date, event date and observation date separately when they differ. A page fetched today is not necessarily a recent signal. Unknown dates remain unknown; use them for background, not a fresh-window claim.

Resolve the actual entity before searching: company/product/person, relevant domain, official accounts, repository, geography and category. Similar names need disambiguation. Dedicated user communities and broader category discussions serve different purposes. A shared name or an unverified handle is not identity evidence.

## Collect useful signals, not mentions

Write a short query plan appropriate to the decision. Search multiple angles only where they add distinct evidence:

- Explicit demand: a request for a solution, alternative, partner or recommendation.
- Pain and consequence: the last occurrence, severity, time/cost, missed outcome.
- Workaround: spreadsheets, manual coordination, scripts, outsourced work or doing nothing.
- Switching: migration, cancellation, a missing capability or an actual comparison.
- Timing: a relevant launch, workflow change, public job posting or business event.

Use original public pages rather than qualify from search snippets. Sources can include professional public discussions, reviews, GitHub issues, first-party pages, changelogs, public company statements and company-owned job listings. Use intentionally shared professional/business information. Do not infer private contact details, scrape private groups, target sensitive personal traits or bypass source restrictions. A source being public does not establish consent to contact its author.

Capture evidence while reading: stable ID, canonical URL or supplied-record locator, entity/author when available, date and date basis, source type, actual access status, concise observation or minimal accurate quotation, and its limits. Save exact customer language when it changes the message. Keep the original wording distinguishable from the founder's and assistant's interpretations. Do not force a quotation quota or report that “all agents returned” when no such work occurred.

A blocked source, an unavailable tool, a failed query and a genuine zero-result search are different states. Retry a transient failure only within a useful bounded attempt; use another permitted route if it supplies equivalent evidence. Do not bypass a restriction, install a CLI or configure a paid provider to make the source appear available. Report partial platform coverage. Stop when the evidence is sufficient for the bounded decision or additional searches repeat the same observations; name the remaining uncertainty.

## Reconcile evidence

Deduplicate the underlying observation, not just wording. A newsletter repeating a forum complaint is one signal with additional provenance. Keep distinct customers separate even when they use the same vocabulary. For jobs, distinct posting URLs/roles must not collapse because the careers boilerplate matches. Separate source/author concentration from apparent popularity.

Retain source and query provenance when clustering. A cluster needs a meaningful shared job, problem or context; adjacent buzzwords are insufficient. Keep contradictory evidence and minority constraints visible. High engagement can help find material to read, but cannot establish truth or buying intent. Diverse sources corroborating the same observed event still do not automatically represent independent customers.

Compare first-party positioning with current practitioner evidence, actual usage, switching and supported benchmarks. A vendor claim is evidence of its promise; a customer's account is evidence of that reported experience. Neither alone establishes category-wide superiority. Distinguish an absence of found complaints from an absence of problems.

### Competitors and public hiring

Resolve each named comparator separately and apply comparable windows, criteria and source-access limits. Include the customer's actual alternatives, including manual work and doing nothing. If the main entity cannot be researched, return the incomplete comparison; never let surviving peers silently replace it. Source volume differences may reflect access or company size rather than product strength. Compare capability, delivered value, buyer effort, cost basis and tradeoffs only to the level evidence supports.

A public job posting can indicate investment, focus or a missing capability. Verify it on the company-owned careers/ATS page when possible, distinguish active from old/reposted roles and avoid counting duplicates. One strategic role can be noteworthy for a small organisation but is not proof of a roadmap, purchase budget or adoption decision. Label inferred themes and the comparison basis; do not turn guessed company size into precise hiring thresholds.

For supplied earlier and later saved findings, compare stable source identities within the same scope: new, continuing, changed and no-longer-observed. “Not found this run” is not deletion or resolution. Produce a requested brief or delta without creating a watchlist, database or schedule. Monitoring requires an explicitly scoped, supported mechanism and verified setup.

## Define and qualify customers

Write a narrow ICP hypothesis: role, company/project state, trigger, urgent job/pain, workaround, buying authority, fit constraints and disqualifiers. Separate user, champion, buyer and approver. Do not promote repetition, praise or willingness to test into willingness to pay. State confidence with reasons and gaps, not a fabricated probability.

For each potential prospect identify a meaningful pain, need or timing signal, why the offer fits, why now, public professional contact context, uncertainty and an evidence-grounded opener if requested. “This company is in the industry” is speculative fit and belongs outside the primary shortlist. Qualification is a research judgment, never a statement that the prospect has consented, is interested or will buy.

Use the original transparent ranking heuristic only when useful: pain strength 25%, product fit 25%, timing 20%, public reachability 15%, evidence quality 15%; each dimension 0–5. Score = sum(dimension / 5 × weight). Typical bands: 80–100 stronger candidate, 65–79 promising, 50–64 material gap, below 50 outside the primary shortlist. These are heuristic ordering labels. A disqualifier or absent meaningful evidence overrides a high score. Never force a score when the inputs are unknown. The structured helper recomputes scores; the agent still judges the evidence.

Modes preserve purpose, not quotas:

| Mode | Emphasis and ceiling |
|---|---|
| quick | Up to five strong prospects |
| standard | Up to ten across useful source types; ordinary default for a full search |
| deep | Up to twenty plus deduplicated pain/trigger patterns |
| design-partners | Testing and feedback, clearly separate from a paid buyer |
| b2b | Companies, current business triggers and evidenced decision roles |
| community | Public discussion and explicit requests, respecting community restrictions |

Respect a user-selected smaller/larger bounded scope; do not pad to a number. Zero qualifying prospects is useful when the search and limits are clear. Return which assumption or source gap prevents a shortlist and the next informative check.

## Complete the requested artifact

A useful prospect report includes verdict, buyer/user ICP, strongest potential prospect, qualified shortlist, speculative watchlist if useful, source/date and score basis, repeated patterns, bounded manual validation plan and limits. Seven days is a useful optional planning horizon, not a fabricated deadline or commitment. Drafted openers are unsent. Use [outreach and learning](outreach-and-learning.md) for a sequence.

For a standalone HTML report, follow [the report contract](../references/report-contract.md), adapt the filled [synthetic input](../assets/example-report.json), run the shipped check/render commands and inspect the actual result. Do not present synthetic examples as research. Preserve the chosen output format; a chat-only request needs no JSON or file. For other requested media, use a real available tool and disclose any uncompleted conversion.

Before delivery, verify unique underlying signals, main-entity identity, dates and access statuses; trace every primary prospect to meaningful read evidence; check buyer/user separation and exact counts; review source-linked claims and opener promises. A valid report file cannot certify any of those judgments by itself.
