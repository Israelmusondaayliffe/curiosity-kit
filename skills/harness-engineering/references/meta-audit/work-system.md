# Work-system audit lenses

Read the [meta-audit contract](../../playbooks/meta-audit.md). These six lenses preserve the original LIFE methods within an explicit harness/work-system scope. They use a user-selected dossier and produce grounded recommendations, proposed policies or transfer plans. Ongoing personal stewardship, inbox/calendar work, portfolio routing and execution of life plans belong to the appropriate work coordinator, including Chief of Staff when available. That owner is a handoff option, not a dependency needed to complete this audit.

Do not gather a public footprint, mine live history or infer a person's values from unrelated activity. Use current stated goals and bounded evidence. General career/life counseling without a work-system artifact is outside this route. Ask for the concrete system or decision to inspect, or direct the broader request to its proper owner.

## Big-picture

Reconcile a scattered work system into a defensible direction. Retain the original question about fulfilling and economically worthwhile work without pretending to know the user's private values.

### Procedure

1. List the projects and commitments actually in the dossier. For each, record its intended beneficiary, delivered outcome, stage, demonstrated demand or use, recurring effort and connection to the user's stated goals.
2. Extract explicit constraints and preferences such as available time, desired work style, collaboration, employment or independent work. Ask about a missing value only if it changes the recommendation. Do not substitute revenue for fulfillment or attention for demand.
3. Identify competing directions and shared components. Distinguish experiments from commitments and sunk costs from future obligations. Explain which work is mutually reinforcing and which competes for the same scarce resource.
4. Compare a few genuinely distinct directions against the stated criteria. Use evidence ranges or unknowns rather than fabricated financial returns. When the field's current direction matters, verify dated primary evidence and separate observed change from forecast.
5. Recommend one near-term direction for the work system and explain the tradeoff. Give a small reversible next step, the work that would pause if accepted and the evidence that would cause reconsideration. Do not cancel anything or notify collaborators.
6. Translate the recommendation into a proposed harness/workflow change. For example, change which brief the intake asks for, the output used to decide progress, or how experiments are reviewed. Keep broad life choices with the user.

### Output, example and limit

Return a project-to-goal map, direction options, recommendation, explicit tradeoffs and a dated decision/checkpoint. A fictional educator is building a course, publishing scattered tool reviews and making workshop worksheets. Supplied customer feedback values the worksheets, while no evidence supports demand for the course. Recommend a short worksheet-focused workshop experiment before expanding the course. The system change is to collect a defined usability result after each workshop and use it in the next planning decision. The report should not declare that the educator has found their life's purpose or forecast income without evidence.

If priorities or financial constraints are absent, show how the recommendation changes under plausible options and ask the user to choose. Do not invent a single direction from an incomplete dossier.

## Most-wrong

Build the strongest case against the user's largest stated bet, then present the strongest counter-case. The purpose is a better decision, not adversarial theater.

### Procedure

1. Confirm the bet, desired result, time horizon, current commitment and what would make the decision consequential. If the dossier contains several bets, identify which is largest under the user's criterion rather than equating expense with importance.
2. Write its causal chain. What must be true about demand, delivery, distribution, capability or timing for the result to follow? Separate observed support from assumptions and incentives to keep believing them.
3. Select the load-bearing assumptions. For each, state the strongest contrary evidence or plausible failure mechanism. Steelman the opposing case without inventing a confident critic or exaggerating weak evidence.
4. Name the observation that would change the decision and whether the current work system would notice it. Check for metrics that hide disconfirming evidence, ignored feedback or no owner for reviewing results.
5. Build the strongest affirmative counter-case using the same evidence standard. Consider option value, learning, asymmetric upside and constraints that make the bet rational despite uncertainty.
6. Recommend a bounded falsification test or decision checkpoint with explicit advance criteria. Avoid rewriting the criterion after seeing the result. Propose a change to how the system captures and reviews evidence if detection is the main gap.

### Output, example and limit

Return the bet, assumption chain, opposing case, strongest counter-case, falsifier, detection gap and proposed next decision. A fictional team assumes reusable prompts will make onboarding twice as fast. Its selected records show much time waiting for access approvals, not drafting. The opposing case is that better prompts cannot remove the dominant wait. The counter-case is that prompt quality may still improve the subset of work after access. Propose measuring active work and approval waiting separately on a matched sample before deciding the next investment. Do not infer the team's motives or declare the product worthless.

If the opposing case rests entirely on speculation, say so. If the strongest counter-case is currently better supported, the audit may conclude that the bet remains reasonable while naming what to watch.

## 10x-or-dies

Test which parts of a workflow may lose value or become more valuable as capabilities and demand change. The name identifies the source lens; it does not require a tenfold forecast or a binary verdict.

### Procedure

1. Decompose the selected workflow into outputs, operations and value sources. Distinguish routine production from judgment, trust, access, accountability, relationships and domain-specific constraints.
2. State the relevant time horizon and current capability evidence. Use primary demonstrations, official product documentation or supplied measured trials where available. Marketing claims and leaderboards do not establish performance on this workflow.
3. Form separate substitution and amplification hypotheses. Specify what a new capability would replace, what it would enable, and the remaining bottlenecks or costs. Record the conditions needed for each hypothesis.
4. Look for counterevidence: reliability failures, integration burden, missing data, buyer preferences, regulation, verification cost or enduring human responsibility. Do not assume technical feasibility means economic replacement.
5. Classify each component as likely to shrink, worth testing for amplification, still load-bearing or uncertain. Give evidence strength and the observation that would change the classification.
6. Propose reversible changes within the selected system and an explicit review date or event. Preserve essential current delivery while testing the new path. A recommendation to stop investing is a decision for the user, not cancellation authority.

### Output, example and limit

Return a component map, substitution/amplification hypotheses, dated evidence, counter-case and concrete experiment. A fictional analyst manually reformats source tables and also decides whether their definitions are comparable. A tested parser may reduce formatting time. It does not prove that comparing inconsistent definitions is automated. Recommend a limited parser trial with reconciliation checks while preserving the analyst's definition review. Report measured time savings only after a real matched trial; until then call them a hypothesis.

If current external evidence is unavailable, deliver scenarios with explicit assumptions. Do not describe them as current market facts or recommend irreversible changes on that basis.

## Decisions-into-policy

Find decisions repeatedly remade from scratch and draft rules that reduce wasted effort without expanding authority.

### Procedure

1. Select dated decision examples from the authorized dossier. Record the question, context, options, chosen action, reason, consequence and reversibility. Do not scan unselected conversations for more examples.
2. Group decisions by the actual rule they share, not by keywords. Identify exceptions and cases where similar language led to different choices for legitimate reasons.
3. Separate cheap reversible choices from consequential, sensitive or irreversible actions. Identify decisions that can be standardized as drafting/triage conventions and those that must remain judgment or approval points.
4. Infer the smallest candidate rule that explains the evidence. Mark inference and ask when multiple plausible rules would change behavior. A one-time choice usually supports a task-local convention, not a permanent policy.
5. Write the proposed rule in one actionable sentence, then specify scope, trigger, exceptions, permitted actions, required approval, evidence source, owner and review/revocation condition. Keep the operational sentence easy to copy without losing its authority boundary.
6. Test it conceptually against the selected past examples and at least one boundary case. State where it would have made the wrong decision. Refine the proposal or recommend no standing rule if the pattern is too weak.

### Output, example and limit

Return the repeated decisions, inferred rule, exceptions, supporting/counterexamples and proposed adoption mechanism. A fictional workshop team repeatedly spends a meeting choosing filenames. Their approved convention consistently uses date and topic. Propose "For new workshop drafts, use YYYY-MM-DD-topic; preserve existing published filenames." This reduces a reversible naming decision without authorizing renaming old files.

A separate pattern involves emailing participants when sessions move. Even if every historical message was approved, do not propose a copyable rule that silently authorizes future sends. Present recipient, information scope and needed user decision through the proper permission mechanism. The audit never activates a standing custom rule or interprets its own proposal as approval.

## Binding-constraint

Find the factor that currently limits the stated result and distinguish it from a loud symptom. A single-constraint conclusion requires evidence; interacting constraints may remain unresolved.

### Procedure

1. Define the delivered result and its measurement period. Trace the work from intake through completion, including queues, rework, handoffs and decision waits. Use actual timestamps/counts where supplied and label estimates.
2. List candidate constraints: capacity, information, access, quality, demand, coordination or a required decision. Identify which step limits completed useful output under current conditions.
3. Test the causal story. If that constraint were relieved, would the desired result increase, or would another unchanged step still cap it? Look for idle downstream capacity, accumulating upstream work and repeated rework, but do not treat any single indicator as proof.
4. Compare competing explanations and measure gaps. Time spent is not automatically the bottleneck. A rare approval may matter more than the task with the most labor; insufficient demand can make faster production irrelevant.
5. Show effort currently spent on non-constraints and its opportunity cost without pretending it has no value. Propose one small move that directly relieves or tests the likely constraint.
6. State the predicted observable result, disconfirming outcome and likely next constraint. Keep the check bounded and preserve necessary quality/authority requirements.

### Output, example and limit

Return the workflow trace, candidate constraints, evidence for the leading one, counterfactual, recommended move and check. A fictional content team produces six drafts weekly but approves two. Dated records show four drafts waiting for one subject-matter decision; formatting takes little time. Propose a brief that resolves that decision before drafting, or a batched review slot if the owner agrees. Predict fewer blocked drafts, not simply more draft volume. Do not create the meeting or assign a person without authority.

If records cannot distinguish slow review from low-quality drafts causing repeated review, keep both hypotheses and request a small matched sample. Do not manufacture one dramatic bottleneck to satisfy the lens's name.

## Bus-factor

Simulate a 30-day absence from the selected workflow and identify the knowledge, access decisions and responsibilities that would stop useful work. Produce a transfer plan without sharing credentials or contacting others.

### Procedure

1. Fix the scenario: the named owner is unavailable for 30 days, beginning on an explicit hypothetical date. Define which services, outputs and commitments must continue and which can safely pause. Do not infer real absence or illness.
2. Walk the workflow over that period. Include recurring deadlines, unusual but plausible exceptions, required approvals, renewals and dependencies that the dossier actually supports.
3. For every step, identify the documented instructions, current owner/backup, location of necessary non-secret information, required access and authority, and evidence that a replacement can use it. A document's existence does not prove a handoff works.
4. Separate knowledge gaps from access gaps and authority gaps. Writing a runbook cannot grant account access; access cannot authorize a decision. Never transfer a password, token or other secret into a document.
5. Rank failure points by time to impact and consequence. Distinguish immediate service failure from temporary inconvenience, and account for safe pause or escalation paths.
6. Propose the smallest durable transfer artifact for each material gap. Include prerequisites, steps, decision thresholds, expected output, validation, common failure and escalation. Name the intended custodian as a proposed role or a verified authorized recipient, not an assumed participant.
7. Design a permitted tabletop or isolated handoff check. A reader follows the runbook against fictional/sample inputs and reports missing steps. Real access changes, delegation, messages or production tests remain separately authorized.

### Output, example and limit

Return a 30-day continuity timeline, dependency register and prioritized extraction plan. Each dependency needs knowledge location, access/authority requirement, failure consequence, proposed transfer artifact, check and unresolved owner decision.

For a fictional workshop, the owner alone knows how to turn registrations into a printable seating plan. A useful artifact specifies the approved registration export fields, duplicate handling, capacity rule, accessibility-note handling, print format and final reconciliation count. It excludes unnecessary personal details and uses fictional registrations for the handoff check. If the print vendor account requires an owner login, record that access dependency without copying credentials or adding another account user.

If no backup owner is authorized, the outcome is a decision-ready transfer plan, not a completed handoff. If the process can safely pause, include that option rather than creating an elaborate replacement organization.

## Close the work-system audit

State the recommendation, its strongest counter-case, evidence confidence, the concrete artifact or decision it changes, and the date or event when the user should reconsider it. Keep follow-through distinct from analysis. No automated monitoring, policy activation, calendar action, third-party assignment or source overwrite is part of these lenses.

When the selected question needs broader ongoing stewardship, return the useful bounded audit first and describe the next owner's job in plain terms. The absence of another installed skill does not prevent completing the local audit or justify inventing that owner's execution.
