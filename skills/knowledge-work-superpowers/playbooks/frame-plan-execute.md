# Frame, plan and execute

Use this method to turn a substantial request into the right result, make an executable plan, or carry accepted work through completion. Its output is the requested brief or plan for planning-only work. For an execution request, its output is completed work with inspected evidence, not perpetual planning.

## Establish the frame without restarting intake

Read the current request, applicable project instructions, relevant existing brief, supplied template and source inventory. A prior plan is context; the user's current instruction governs scope. Resolve discoverable facts through approved files or their owning connector before asking the user.

Identify the following in a short working note, or internally for a small task:

- **Outcome:** what must exist and what it must let the reader decide or do. “Research onboarding” is an activity; “a cited recommendation choosing a two-week onboarding pilot under the stated staffing limit” is an outcome.
- **Reader:** their role, known concepts, decision and useful depth. Do not invent their opinions, expertise or authority.
- **Questions:** which questions must be answered, what is excluded, and which answers depend on others.
- **Sources:** the records that own the facts, allowed source set, date/version cutoff and accessible versus missing material.
- **Constraints:** requested format, length, template, destination, deadline, confidentiality, exact protected wording, prohibited actions and relevant authority.
- **Success:** observable requirements such as complete option coverage, direct support for decisive claims, disclosed conflict, correct units and a usable final file.

Preserve what is already settled. A complete authorized brief needs no second approval. A material choice between different deliverables needs a focused question if it cannot be inferred. If the user asks for several deliverables, inventory all of them; do not frame the first and silently forget the rest.

Classify unresolved points before asking:

| Missing item | Next action |
|---|---|
| Fact in an accessible approved source | Inspect it. |
| Low-risk detail consistent with the request | State a reasonable assumption when it affects the result and continue. |
| Consequential user preference or authority | Ask the specific decision; hold only dependent work. |
| Knowledge held by a named expert | Prepare a focused question or questionnaire if requested; do not manufacture the answer or send it without authority. |
| Question whose prerequisites are unresolved | Record the precise blocked question and prerequisite. Ask it when ready. |
| Unspecified but in-scope topic | Clarify its role before planning detailed downstream work. |
| Outside the request | Exclude it or propose it separately; a planning note cannot authorize it. |

Ask independent ready questions together when helpful. Do not ask the user to answer something a pending source read should resolve. Recompute readiness when new answers arrive.

For a questionnaire, identify the recipient's role and the facts or decisions they alone can supply. Explain the purpose, provide only necessary context, place the highest-value questions first, and leave answer spaces. Allow “unknown” or partial answers. Include a deadline only if one is known. A local draft is a complete deliverable when that was requested; it is not evidence of having contacted the expert.

## Choose an approach only when it matters

When a real choice remains, compare materially different approaches against the same brief. Include doing nothing when it is a credible alternative. Record evidence, assumptions, cost or effort, risks and the condition that would reverse the recommendation. Do not force three options when two or one are all the task supports.

A useful prototype is a small actual artifact that answers a named uncertainty. For example, draft one filled comparison section to find whether available evidence can support the proposed decision, or render one representative page to inspect legibility. Record the question, inputs, observation, limitation and design consequence. A readable page does not prove reader comprehension; a persuasive pitch does not prove demand. Keep preference choices with the user when empirical evidence cannot settle them.

When combining alternatives, read each whole candidate, choose a coherent base and adapt only compatible strengths. Recheck the result against the original evidence and constraints. Do not average incompatible recommendations or splice paragraphs that use different definitions.

## Plan reviewable work, not administrative ceremony

Use the selectable [plan record](../assets/work-record-templates.md). One compact note can contain the brief, plan and progress. Create separate artifacts only where useful for loading, collaboration, durability or the requested delivery format.

Each substantive work unit should state:

1. Requirement or question it satisfies.
2. Exact inputs and prerequisites to inspect.
3. Concrete operation or judgment needed.
4. Output the next unit or reader will use.
5. Evidence standard and observable check.
6. Stop condition, unresolved choice or authority boundary.
7. Owner and allowed write location if work is shared.

Split where one result could be accepted while another is rejected. Keep tightly coupled extraction, interpretation and writing sequential. Batch repeated same-shape extraction when it saves overhead without mixing source identities. Do not make one worker, ticket, commit or report per paragraph.

Carry exact constraints once in a canonical brief. When one task consumes another's output, compare what is actually produced with what is needed: definitions, units, date windows, source status and format. Do not plan downstream claims as if a still-unknown answer were settled.

Before execution, check:

- Every required deliverable and template section has an owning task.
- Inputs are actually available or their absence is named.
- Dependencies can be satisfied in the proposed order.
- “Add sources,” “improve quality” and similar vague steps have been replaced by an inspectable question or result.
- Proposed checks can fail for the relevant defect and concern the final artifact.
- No step silently adds a send, purchase, account change, installation, schedule or deletion.

A plan is not an authorization source. If the user requested a plan only, deliver it and stop. If the request already authorizes execution, continue through ready units without routine “shall I continue?” pauses.

## Execute with evidence and recoverable state

Read the complete plan and brief at startup. Resolve contradictory constraints or unavailable essential inputs before dependent work. Correct a small plan defect inline only when the intended outcome and authority are clear; record a consequential interpretation and its evidence. Otherwise ask the material question.

For each unit:

1. Reopen the exact relevant task, constraints and source clauses. Memory of a summary is not a substitute for exact values.
2. Inspect prerequisite outputs rather than trusting a worker's “done.”
3. Perform the authorized work using the corresponding [research](research.md), [analysis/drafting](analyze-and-draft.md) or [review](review-and-repair.md) method.
4. Inspect the output and run the relevant check. Read the result, including failure or unavailable evidence.
5. Record the artifact/version, actual check, open finding and next action. Mark complete only when the named requirement has evidence.

For work that may span sessions, bind progress to a stable task description or task ID, the actual brief/source locations and their relevant versions, intended output location, completed results and outstanding dependencies. File names alone are insufficient: two unrelated `plan.md` files do not share completion state. A later worker must be able to open the actual artifacts, not only a summary of them.

On resume, compare the record with the current request and files. Verify that completed artifacts still exist and that critical evidence has not changed. Reuse valid unchanged work. If a source or requirement changed, reopen affected claims, computations and conclusions; preserve unrelated settled outputs. Missing temporary files mean missing evidence, not proof the work never happened and not permission to declare it complete.

Replan when a governing source contradicts an assumption, the user changes the decision, evidence becomes unavailable, or a task no longer serves the brief. State the specific change and affected scope. A source access failure blocks claims that need it; it need not stop every independent section.

## Finish or stop honestly

After the plan's units are complete, compare the actual artifact with all original requirements and open findings. Use [verify and deliver](verify-and-deliver.md). Do not finish with only progress notes when the request was for a complete report.

If repeated attempts reveal the same unresolved cause, stop repeating that approach. Inspect the cause, change the method within scope or name the missing source/tool/decision. Exhausted effort does not make a defect minor. Preserve useful completed work and give the exact next action required for the blocked part.
