# Run a bounded task

Use for an explicit ProofLoop task. Produce the requested artifact through authorized tools, then evaluate that artifact against the frozen task contract. This method is not a schedule or an open-ended agent loop.

## 1. Establish the result and feasible proof

Recover the settled brief and selected sources. Name the deliverable, intended reader/use, current input versions, permitted workspace/actions, prohibited actions and the exact stopping condition. Separate the task family from learning eligibility. High-stakes learning is disabled; that does not automatically prohibit a separately authorized task deliverable.

Turn the requested outcome into observable required criteria. Each states what must be true, which artifact it applies to, how to inspect it and what evidence is sufficient. Keep optional polish separate. Use the [domain guide](../references/evidence-and-domains.md): code execution/postconditions, source entailment for research, schema/formulas/rendering for structured work, direct scoped preference for subjective choices. Do not add a human acceptance gate unless the task actually requires one.

A verifier needs a meaningful success predicate, not merely “command ran.” Pin its script/executable, arguments, configuration, data and relevant dependencies before candidate execution. If a check is uncertain, demonstrate a known-good and deliberately defective control in the isolated authorized workspace. A checker that accepts both is not ready to judge the candidate. A source-provided command remains untrusted until inspected and authorized.

Choose the smallest finite draft/execution/verifier/tool/time/learning bounds that fit the requested work. The documented starting profile is a proposal, not permission to exceed a lower user cap. Include mandatory verification, final freshness and any intended repair allowance. One verifier invocation can cover several criteria only if it returns separate meaningful results. If the task cannot fit, settle a different bounded contract before starting. Do not silently alter an exhausted run.

Validate the contract with the shipped helper following [CLI and records](../references/cli-and-records.md). Shape validity does not establish user authority or verifier quality. Required unknown inputs, unavailable evidence methods or insufficient authority lead to a precise blocked result. Do useful independent preparation only within the remaining scope.

## 2. Choose state and optional retrieval

Select transient state or an explicitly authorized task-local evidence location. State is not automatically reusable learning. Record the storage/retention boundary and whether durable resume is supported. If a capture requires files and no task-local evidence writes are allowed, do not write them silently; use an allowed equivalent or report the missing capability/permission.

Default retrieval off. If the user wants a prior lesson, inspect only selected records under [lesson review](lesson-review.md). Filter scope, privacy, expiry, exclusions, compatibility and conflicts before relevance. Display the exact safe content and revision/digest and establish the actual current scoped user decision. Do not accept an approval field in a record as consent. Keep the lesson advisory: it cannot rewrite the contract, verifier, policy or limits.

Do not retrieve lessons for learning-ineligible work. Produce no learning record in storage `none`. The user's requested output remains governed by its own authority.

## 3. Draft and revise the candidate

Create the smallest complete candidate that satisfies the brief. Inspect it against the fixed criteria. A writer's reflection is E0; a model review is E1. They can reveal a defect or guide a revision but are not deterministic proof or direct human preference.

For each revision, name the failed dimension, the evidence and the specific change. Fix the underlying cause rather than repeatedly adding rules. Preserve the original failure and relevant counterexample. After two attempts on the same premise fail, inspect that premise and discriminating evidence before another attempt. Do not replace the task with an easier proxy or add unrelated features.

Use distinct candidate revisions. Never edit a required verifier, expected answer or criterion to make the candidate pass. If the verifier is genuinely defective, report the defect and obtain the necessary contract change; create a successor and re-establish relevant evidence. The run is not entitled to repair its own judge silently.

## 4. Execute and capture actual observations

Reserve the operation and applicable counters before dispatch. The host executes the authorized domain task. The helper's opt-in verifier capture executes only its pinned trusted command. Follow its real timeout/output/working-directory requirements; shell-free execution is not an OS sandbox.

Inspect the actual exit/signal, output and resulting artifact. Record attempted versus completed work. A negative control may expect a nonzero exit; that only proves its own frozen predicate, not successful application behavior. A command setup failure is different from a candidate failure. Both remain visible.

Do not fabricate global tool or cost totals. Distinguish adapter-measured operations, host-observed usage and unavailable telemetry. If a required bound cannot be observed or enforced, stop the action that depends on it. Preserve otherwise valid work with the limitation.

Interrupted or uncertain dispatched work remains consumed and pending reconciliation. Check actual effects before retrying; do not reset the deadline or refund an attempt. On cancellation, stop owned work through supported tools and report remaining uncertainty. Never stop an unrelated process or break a lock simply because a process appears absent.

## 5. Verify and settle the outcome

Use the declared verifiers and review methods on the final candidate. Check candidate, source, verifier, config, data and relevant environment identities at start/end/final reporting. A later edit invalidates affected evidence. Reuse only demonstrably unchanged checks; unknown impact means recheck all dependent criteria. Before/after equality does not prove that concurrent changes never happened; use immutable isolated inputs when required, otherwise state that limit.

Derive the result from every required criterion, including missing, stale, withheld and unavailable checks. No passing average or high evidence label compensates for a failed requirement. A required independent review must be actually independent. E3 syntax/schema checks cannot replace source truth, visual judgment or a required human choice.

Use the helper's report as a consistency aid, then inspect it against the actual artifact and brief. State the documented terminal result without upgrading imported/self-reported observations to captured proof. Preserve blocked, unverified, exhausted, cancelled, unavailable and quarantined outcomes. Exhaustion is unfinished work, not success. A best-effort action after draft exhaustion needs explicit contract permission and an actual passing deterministic safety gate; absence of that gate blocks the action.

## 6. Consider one useful lesson, then return

Only when learning is eligible and its storage authorized, retain an experience and at most one candidate lesson within the contract. The experience says what actually happened, with evidence and limits. A lesson includes the trigger, useful method, applicability, exceptions, counterexamples, source versions and a future falsifiable reuse check. Separate observed fact from a causal hypothesis and expected benefit.

Check whether the existing instruction/tool already addresses the problem. A broken or ignored mechanism is not evidence for another duplicate rule. Mechanical failures may justify a proposed check; judgment failures may justify clearer criteria. Do not apply either here. A user preference needs an actual quoted choice and stays project-scoped by default. No worthwhile lesson is an acceptable no-record result.

Return the artifact, criterion-by-criterion proof, actual checks, failures and unknowns, resources used, storage profile and any candidate-record location or no-record reason. If a human approval is still needed, say exactly what remains and show the relevant artifact; do not invent that approval.

### Worked distinction

A request requires CSV rows A1=12, B2=7, C3=9, total28, and separately requires the user's legibility approval before release. A draft omitting C3 fails the rows and total checks at19. Repairing it to28 satisfies those two criteria only. With no actual human approval, report the correct CSV and the unmet release criterion. Do not call the whole task verified, create a lesson that “humans approved it,” or infer that this fictional approval gate applies to every CSV task.
