# Proof and tools

Choose the observation that would actually establish the requested result. The host's available tools, current permission and actual output format determine the route. A named tool in Markdown does not make it available.

## Match proof to the domain

| Work | Useful actual proof | What the proxy misses |
|---|---|---|
| Research | Inspect decisive source passages, reconcile contradictions and reproduce important calculations | A long source list or valid citation syntax does not prove truth or a full read |
| Writing | Read the complete text against required content and source meaning; exercise the reader's intended action; open/render the required export | Grammar and section checks do not prove a usable argument, accurate promise or readable layout |
| Creative assets | Inspect the delivered media against the agreed brief, references, composition, dimensions and duration | A good prompt or storyboard does not prove the generated output or playable media exists |
| Operations | Run one authorized safe request through intake, decision, action and confirmation; exercise the important exception/recovery path | A written procedure does not prove the process works or an external effect happened |
| Data | Reconcile totals to independent examples, inspect formulas/units/denominators and recalculate | A copied expected formula can agree with the same error in the implementation |
| Communication | Inspect verified recipient, facts, tone, requested action, links and attachments; verify sending only when authorized | Draft readiness and content approval do not authorize sending or prove delivery |
| Personal plans | Check actual time, travel, energy, budget and dependencies from permitted current sources | A checklist does not establish feasibility or future adherence |
| Software | Run public-interface behavior checks, relevant builds and real interaction/regression paths | A mock, internal call counter or green unit suite can miss the user-facing failure |

Record input/source version, action, expected result, actual result, evidence location and what was not checked. For a service, confirm the resulting persisted state when required. Do not replace missing access with an invented check. A synthetic fixture proves only the conditions exercised.

## Use existing capabilities first

Prefer the host's native supported tool for retrieval, file production, rendering, source control or delivery. Then use a standard-library operation when appropriate, then an already installed dependency. Never install software, create credentials, enable a service or execute a donor bootstrap as an implied step.

- Ordinary chat work needs no Python or files.
- Canonical record validation needs Python 3.9+ and read access to selected local files.
- PDF/document/spreadsheet/media generation and viewing need the corresponding actual format tool. If absent, preserve the useful draft and name the missing production or inspection result.
- Live source retrieval needs an authorized browser/connector; supplied-sources-only work does not authorize broader research.
- Delegation needs supported host workers and assigned disjoint scope. Sequential work remains valid when workers are unavailable.
- External delivery needs a supported authorized action and observed result. A file location or a status word cannot establish it.

## Bundled helper

`python3 /actual/skill/root/scripts/check_outcome.py --help`

Read the [exact checker contract](checker.md) before creating a machine-checkable record. Modes are brief, review, plan and experiment. The script reads explicit files only, performs no writes or network calls and never executes the proposed work. It replaces the originals' four small validators without introducing an engine or persistent store.

Use it when authoring the canonical local records. A custom user format remains valid; apply appropriate manual/format checks rather than create a duplicate shadow artifact. If the execution tool is unavailable, identify the CLI as unrun. A specifically required checker gate remains incomplete.

Structural consistency is not source truth, real approval, experiment validity, immutable storage, completeness of the prose, quality, installation or delivery. A dependency-ready report is derived from declarations and still needs actual evidence/authority inspection. The example inputs are fictional and cannot authorize actions or prove user outcomes.

## Evidence reuse and changing sources

Proof applies to the artifact and conditions actually checked. If a later source changes a quantity or allowed claim, inspect every affected output, record, caption and final answer. Retain unaffected valid proof. If an artifact changed after approval, identify whether the change affects the approved scope and current version. Do not inherit approval by filename.

Preserve native failures and invalid runs. A reviewer can correct a final output, but the corrected output does not make the original unassisted run pass. A fixed catalog or matched nominal model does not establish isolation when unrelated metadata, tools or source reads differ. Use scoped within-host comparisons and disclose missing baselines; a single exercise is not statistical superiority.
