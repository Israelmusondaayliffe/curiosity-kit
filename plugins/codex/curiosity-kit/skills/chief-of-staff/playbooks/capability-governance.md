# Capability governance

Answer what capabilities exist, what fits, what overlaps and what is actually ready. Keep the [entry's authority](../SKILL.md#authority-lives-here) and [host contract](../references/host-contract.md). A read-only audit may create its requested evidence in an owned output location; it does not change the inspected setup.

## Inventory the right layer

Start from the requested scope: a selected skill, installed plugin, workspace, host or proposed library. Record actual host/surface and accessible roots/catalog. Prefer a supported native listing, then inspect only necessary package metadata and full relevant entries/resources. An inaccessible root is an error or coverage gap, not an empty inventory.

For each relevant capability distinguish intended source identity, packaged bytes, installed/enabled state, host discovery, invocation eligibility and observed behavior. Record exact name, namespace/aliases, version/ref where known, resource locations, prerequisites and evidence. An entry file alone cannot prove supporting-resource parity. Resolve symlinks and duplicates within authorized boundaries; do not follow arbitrary links into private/global roots.

Use an existing project inventory if suitable, updating only the requested scope with actual evidence. Do not introduce a registry service. Preserve unknown status rather than manufacture a complete table. Source-ready, candidate, accepted, installed and verified should never collapse into one “available” flag.

## Resolve selection, names and overlap

Read the complete relevant methods before claiming equivalence or recommending a skip. Compare purpose, trigger/negative cases, inputs, output, essential branches, tools, activation/authority, failure/recovery and check contract. Same name or identical SKILL.md does not prove two full packages are interchangeable; different names can conceal duplication.

Classify overlap: exact duplicate bytes, shared obligation, complementary workflow, deliberate host variant, alias, stale mirror or genuine conflict. Use hashes to establish bytes, then explain functional consequences. A keyword/substring match is only a routing candidate; quoted or negated names and historical examples must not trigger work.

Recommend one canonical owner per obligation, with aliases pointing to it and distinct requirements preserved. Check actual callers, references, scripts, metadata, fixtures, licenses and packaging before proposing a merge/removal. Compare meaning within a sentence/bullet as well as across files. Examples can demonstrate a rule; they should not become conflicting second rules. Do not delete or rename anything from the audit alone.

## Assess readiness and discovery honestly

A frozen source/manifest identifies what was inspected. Relevant static validation checks frontmatter, resource/link closure, declared tools, loader behavior and packaging. Meaningful behavior checks use actual requests and final artifacts. Fresh-host discovery must observe the selected installed package's actual catalog/read/invocation, with required resources and negative controls; a supplied prompt or substring count is not that proof.

Do not demand whole-host catalog equality when dynamic builtins legitimately vary. Bind the selected plugin and input/output/read/write boundary. Disclose dynamic host tools separately. A self-denying permission pattern can invalidate qualification; inspect the generated actual rules for the selected helper path before inference without broadening global access.

For package/cache/source parity compare every relevant runtime resource, not only entry names or Git HEAD. Include dirty working bytes when the task permits them; preserve unrelated staged, unstaged and untracked work. A shaped hash, `verified:true`, exit zero or caller-written log is an assertion until connected to the actual artifact and observation. Keep invalid/missing checks in the result and preserve their denominators.

Report the narrow state: source inspected, candidate built, selected package validated, installed/discovered, behavior verified in a stated scope, blocked or unrun. No single tier or score proves all surfaces, API access, publication or production readiness.

## Maintain and improve the portfolio

Use observed lifecycle states and ownership: proposed, written, qualified in bounded scope, accepted by the actual reviewer, privately delivered, installed or retired. Retain earlier acceptance limits and exact evidence; a newer candidate does not invalidate unrelated accepted units. A deprecation proposal needs a replacement, caller impact and migration evidence before actual retirement.

For a requested harness audit, select only the useful [governance lenses](../references/governance-lenses.md). Ground findings in concrete tasks, errors, cost and missing outcomes. Avoid a compulsory sixteen-lens report. Turn a finding into the smallest actionable recommendation, with owner, affected paths and meaningful proof. Repetition in past work may justify a proposal, not automatic standing policy.

Harness Engineering owns reusable skill/harness authoring, Skill Creator Pro, Skill Eval Loop, context reduction, packaging and guarded setup changes. Model Prompt Lab owns task-prompt work/comparisons. Other specialists retain domain craft. Hand over exact observed defects, current inputs, desired outcome and authority; do not build a second creator/evaluation engine inside Chief of Staff.

If an owner is unavailable, finish the inspectable inventory/proposal or other independent core work. Do not claim its specialized build was performed or copy a generic method over an essential missing capability. State the prerequisite and supported next step.

## Prepare installation, release or whole-harness adoption

When the user requests adoption, establish the selected hosts, instruction layers and desired routing behavior. Adoption may require a whole supporting-instruction rewrite for the selected Claude or Codex setup rather than appending a routing sentence; the current task determines that scope. A request to plan that work ends with a proposal. When actual application is authorized, use the available Harness Engineering method and [adoption checklist](../assets/adoption-checklist.md); this playbook owns the governance handoff, not a substitute install engine.

Inventory the actual current AGENTS/CLAUDE/project/user instruction layers, enabled plugins, relevant settings and ownership. Back up only the scoped readable files to a private owned location; do not collect credentials, auth databases or unrelated personal state. Preserve useful existing requirements and platform precedence. Preview removals, additions, conflicts and routing changes. Even a concise adoption proposal identifies the scoped recovery copy, rereading changed files against the approved text, and verifying any restore before it can be called recovered.

Keep Chief of Staff's ordinary selection policy separate from protected skill activation, action permissions and host enforcement. Native metadata differs across hosts; inspect the installed version's supported mechanism. Do not promise a hard Chief-only lock. Do not bypass a denied call, automatically register a schedule or export a private plugin publicly.

Use selected build/validation and actual supported installation. Verify remote delivery, installed/cache identity, fresh discovery, direct specialist use and Chief of Staff composition separately. Keep host-specific failures and unrun paths. Observe actual restoration/cleanup; never label a pending install or rollback complete from its written plan.

## Deliver the useful finding

Lead with the actual result, concrete required gaps and the smallest next action. Link inspectable evidence when available. Keep source-to-candidate mapping and full audit material out of ordinary runtime context unless the user requests that audit. Stop when the requested scope is answered; do not expand into a full portfolio campaign because more files exist.
