## System-review example

# System Review

This separate example uses fictional supplied records W1/W2. W1 lists ten internal request handoffs: seven waited for an approval owner, three did not. W2 says two teams disagree about who may approve exceptions. These facts demonstrate the example method only.

## System and user

Internal request triage serves an operations team. The recurring trigger is a submitted request, with ten requests in W1's observed period. A request must reach the appropriate human decision owner; missed required approval is unacceptable. Future volume is unknown.

## Current-state map

Intake records the request, an assistant drafts a recommendation, two team queues each expect the other to approve exceptions, and an operator waits before replying. W1 records seven approval-owner waits. The request and approval evidence remain in the existing task record; no new system is proposed yet.

## Diagnosis

The observed issue is conflicting ownership in W2, consistent with the waits in W1. Causation and future time savings are not proved. This is primarily an authority/process question to resolve, not evidence that another AI tool is needed. Baseline: seven of ten observed requests waited for an owner; elapsed time was not supplied.

## Friction candidates

### Clarify one exception owner

Keep the existing task record and make the authorized exception owner explicit. This could reduce repeated routing decisions while preserving human approval. The risk is assigning authority the team has not granted. Recommendation: strong enough to discuss, not to implement without the owner's decision.

### Keep the current process and observe

Use the existing queues while collecting actual wait durations for a bounded period. Lower change risk, but the known ownership conflict remains. This is a valid fallback if authority cannot yet be settled.

## Top recommendation

Ask the responsible decision owner to settle exception authority, then pilot one documented routing path. Do not automate an unresolved approval decision.

## Future-state allocation

A human owns exception approval. AI may summarize the request and evidence. Existing deterministic routing can attach the chosen owner only after the rule is accepted. Remove duplicate routing questions only if the pilot shows that they provide no separate control. No new service or data store is required.

## Controls exceptions and recovery

The request cannot leave review without the required human decision. Unknown exception type returns to the named owner. A missing approval record or conflicting owner is a stop signal. The operations owner restores the prior routing path and retains request history if the pilot fails. No record is deleted.

## Right-sized pilot

- Scope: Five synthetic internal requests after the authority decision.
- Owner: Proposed operations owner, to be confirmed before execution.
- Baseline: W1's seven owner-waits in ten observed requests, not a measured turnaround-time baseline.
- Success signal: Each synthetic request reaches its correct named approver with no lost required approval.
- Stop: Any missing approval, conflicting owner or out-of-scope live request.
- Rollback: Restore the prior routing rule and retain both versions and request evidence.
- Review date: Proposed October 12, 2026, subject to owner acceptance.
- Exclusions: Live requests, external messages, new accounts and tool installation.

## Decisions needed

The responsible human must settle exception authority, accept the pilot owner/date and authorize any pilot execution. These are proposals, not assigned commitments.

## Proof after pilot

Inspect every synthetic request's input, chosen owner, approval record and final state. Report failure or inconclusive evidence honestly. Only observed pilot behavior is established; production savings and rollout remain unproved.

## Handoff

For a real continuation, keep one compact note with these fields, in prose or the user's native task format:

- Task identity and the actual requested outcome.
- Governing source/brief versions and accepted decisions; proposals and unknowns separate.
- Current artifact paths/versions and who owns each writable file.
- Completed results with actual check, result and evidence location.
- Open findings, stale evidence, blocked dependencies and current approval/action limits.
- Next dependency-ready step and the observation or decision needed to proceed.

A record can say a CLI was unavailable, an artifact is a private draft or a test is invalid. These are useful states. Do not copy a false completed checkbox, live credentials or unrelated private history into a handoff.
