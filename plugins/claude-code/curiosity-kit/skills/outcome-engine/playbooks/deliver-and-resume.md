# Deliver and resume

Use this method to execute authorized work and prove the result, or to resume without repeating completed work or external effects. Read the accepted brief, the selected slice and its real dependencies. A request to review or plan does not authorize execution.

## Establish a valid starting point

Confirm the current task identity, permitted locations/actions, governing source/brief versions, relevant artifact versions, open findings and available tools. Inspect the actual dependency outputs and evidence rather than trusting a completed checkbox. Resolve consumed/produced interface mismatches before building on them.

For a resumed task, read the current progress note, actual files and relevant change history. The same filename may contain a new source, another task or edited work. Reuse valid proof for unchanged material; reopen only affected work when sources, approval scope, requirements or artifact bytes changed. If identity cannot be established, report the uncertainty and inspect further rather than starting again from memory.

## Work one observable result at a time

1. Define the check at the interface the recipient actually uses. State the expected result and its independent basis. [Proof and tools](../references/proof-and-tools.md) gives domain examples.
2. Establish the current state. Observe the failing behavior, missing artifact or unverified requirement without destructive demonstration. A check that already passes may be a useful regression check, but it cannot prove your later change caused success.
3. Make the smallest useful in-scope change that can satisfy the check. Do not add imagined future cases or replace the approved outcome with an easier proxy.
4. Run the actual check on the changed artifact. Read the full relevant result, including failures and omissions. A command's exit code, a screenshot or a worker summary may be necessary but insufficient.
5. Compare with the accepted requirement. Resolve important failures or leave the result explicitly incomplete. Simplify when it preserves the behavior, and rerun only the checks affected by the simplification.
6. Record the artifact/version, observation, check/result, evidence location and unresolved limits. Then take the next dependency-ready authorized slice.

An end-to-end mandate can cover several slices. Continue within it without a new approval ritual after every result. Stop at an actual change of authority, a material user-owned decision, a missing required tool/source, exhausted agreed resource bound or an essential failure whose next safe step is unknown. Keep independent permitted work moving where useful.

## Verify meaning and the complete output

Structural checks do not read intent. Compare the whole output to every accepted requirement, including the small final-answer constraints. Inspect titles, captions, source notes, records and email drafts as well as the main body. Preserve exact numbers, conditions, dates, denominators and uncertainty throughout. A correct main memo does not excuse a prohibited population claim in its evidence record.

Recompute important quantities from independently checked inputs. Do not derive the expected answer with the same transformation being tested. Inspect actual source passages and record partial/inaccessible sources honestly. A source's causal explanation is not your observed causation. An authored plan cannot establish approval or an external effect.

For a multi-asset result, run the recipient's whole path: can they find the governing version, use each promised artifact, understand the next action and see which approvals remain? Check cross-asset facts, filenames/links, required attachments, format and boundaries. Verify usable output through real available viewers or tools when the task requires rendering or interaction. If PDF export or playable media is required but unavailable, name that missing result rather than renaming Markdown or a script as the completed deliverable.

Check that all required slices and integration checks are satisfied. Distinguish requirements coverage from evidence quality and delivery status. A canonical checker pass means its declared structural rules held; it does not grant acceptance.

## Diagnose a failed proof

Separate these causes before changing more work:

- Input/source problem: missing, stale, contradictory, out of scope or misread.
- Plan problem: wrong dependency, impossible contract or an omitted requirement.
- Observation problem: a check that never exercises the real behavior, a stale artifact, an incorrect expected value or a noisy/unmatched comparison.
- Implementation problem: the permitted action produced the wrong result.
- Authority/tool problem: the needed step cannot be performed under current permissions or capabilities.

Preserve the failed observation and exact version. Reproduce safely where needed, form one causal hypothesis and change one relevant variable. If the check was wrong, correct its contract separately and retain the earlier failure/invalid label. Do not rewrite history to make a run pass. Repeated failures without new evidence need a changed diagnosis, not another blind attempt or a larger agent group.

An important required defect remains unresolved even when a fixed repair budget ends. Report partial or blocked work with the exact next condition. Do not label parked failures complete.

## Interrupted actions and recovery

Before retrying an action with an external effect, inspect what actually happened through the supported service or artifact. A timeout is not proof that nothing was sent, created or charged. Use an existing operation ID, current state or receipt to reconcile; retry only when the prior effect is ruled out or the supported operation is idempotent and authorized. If status cannot be established, pause that action and name the uncertainty. A local plan checker provides no service reconciliation.

For interrupted local work, preserve current artifacts and relevant evidence. Use a known safe copy/version when available. Do not reset a branch, overwrite user edits, delete temporary-looking files or roll back external changes without the relevant authority. Recovery instructions describe permitted options; they do not add permission.

## Handoff and finish

Use one compact [handoff record](../assets/work-records.md#handoff) for work that outlives the current context. It names the task, governing brief/source versions, owned files, actual completed outputs, evidence, unresolved questions/findings, current approval/action limits, and next dependency-ready step. Include enough exact context for a fresh worker, but do not copy credentials, unrelated history or a whole private archive.

Return the result first, followed by actual verification and material limits. Use an honest state:

- Completed in the agreed scope: required artifacts/actions and their meaningful checks are done.
- Ready for the named approval: production is checked, but the actual approval gate remains open.
- Partially completed: useful outputs exist, with named required work unfinished.
- Blocked: the remaining action needs a specific source, decision, tool or authority.

A delivered file can be complete while later real-world benefit is unobserved. A draft is not sent. A local path is not a verified user-accessible link. If the user authorized delivery through a supported channel, perform that bounded action and verify its result. Otherwise stop at the private artifact or handoff. Do not claim live impact, fresh routing, installation or a provider operation from a simulated or source-only check.
