# Context doctrine

Keep one model-agnostic skill with small host adapters. Put conditional detail beside the workflow that needs it; keep frequently needed instructions directly available. Optional helpers may compose with the skill, but essential methods and dependencies must work without sibling skills.

## Preserve what matters

Preserve stable user policy, authority boundaries, source routing, voice, and task-specific acceptance criteria. Place rules in the smallest scope that serves their consumers. Do not broaden workflow-specific authority into global policy or remove necessary rules from independently executed prompts.

Treat repeated instructions and suspected model compensation as hypotheses for subtraction, not automatic defects. Model capability, a newer release, or fewer tokens is not evidence of correctness. Replace demands to expose hidden reasoning with concise rationale, calculations when useful, or observable work evidence.

## Test the smallest change

Before deleting or moving instructions, capture the current behavior on representative cases, including authority, routing, failure handling and the requested outcome. Hold model, settings, tools, inputs and scoring conditions fixed between baseline and candidate. Repeat where variability or risk warrants it.

Change one coherent group. Accept subtraction only when required behavior and qualitative criteria remain satisfied without material regression. Restore or repair a failing change; do not weaken acceptance to make it pass. Verify moved references actually load. Measure context savings if claimed.

Keep meaningful verification. Prefer existing executable tests and observable state checks for repeatable requirements. Exercise the real relevant surface, preserve evidence and clean up owned test resources. A parser, report or plan cannot substitute for the requested working result.

## Adapt without accumulating machinery

Respect the user-selected model. Otherwise choose a capable available model suited to the work and required tools, considering cost without blindly choosing the weakest. Inspect actual host capabilities; consult current official documentation when a model-specific decision requires it. Do not embed permanent model names, versions, prices or effort assumptions. A model upgrade normally calls for rerunning relevant acceptance checks, not rewriting the skill.

Add no registry, model catalog, routing subsystem or compulsory ceremony. Use independent review when risk warrants it. Completion means the agreed result is demonstrated and required work is resolved.
