# Animate references, edit, extend or join

Read the actual supplied images/video and use the [common contract](../../references/contract.md). Select the exact family/version/operation/surface [profile](../../references/models/index.md), then this method's relevant branch. Examples in [animation templates](../builder/assets/animate-templates.md) are optional structures, not universal transport schemas.

## Bind the assets

List actual upload order, visible identity/content and intended role: opening frame, closing frame, character, wardrobe, style, composition, camera/motion, soundtrack or source clip. Give each property one controlling source and name material exclusions. An identity sheet is not automatically an opening frame; a board grid must not become the visible video. If two images could be either endpoints or different-role references and the distinction changes the result, ask which.

Specify subject motion, camera motion, environmental motion and protected still elements separately. Avoid redescribing or redesigning a supplied image unnecessarily when the selected model expects motion-first instructions. Maintain physical paths, contact, scale, screen direction and coherent background parallax. Use exact native reference roles only when supported; descriptive labels never establish uploaded control bindings.

## Select the operation

- **One image to motion:** establish how the observed opening state changes, how quickly, where motion ends, and what stays fixed. A static camera is a valid choice. Preserve requested visual medium and identity.
- **First/last frame:** bind actual clean endpoint assets to documented native fields where available. Describe the plausible intervening action, optional midpoint only if useful, and arrival in the supplied final composition. Distinguish hard API endpoint conditioning from an approximate prose request. Do not force a dense timed sequence onto two sparse keyframes.
- **Multiple references:** separate identity, costume, style and motion contributions. A motion reference cannot transfer an unwanted person or background. Give scene-specific activation for multiple subjects, with unambiguous labels and interaction positions.
- **Visual edit:** state source clip, target object/region, desired change and temporal scope. Preserve unselected content, camera, action, lighting, duration and audio as applicable. A mask/box is a real asset or UI selection, not a control invented by writing “boxed.” Ask for missing localization if it materially determines the edit.
- **Audio edit:** state the component to change, interval, replacement or silence, and protected speech, timing, lip sync and ambience. The mere presence of background music does not make a generation request an audio edit. Confirm this native mode exists before submit-ready claims.
- **Forward extension:** describe only new footage after the observed terminal state; inherit subject, camera, light, motion and sound. Do not regenerate old events. Native extension versus a separately generated continuation/composited join must be named honestly.
- **Backward extension:** begin before the source's opening state and arrive continuously at it. Preserve source footage, define the new lead-in duration and endpoint contact, and verify actual pre-extension support.
- **Clip join:** identify both boundary states and write only the connective action needed to bridge them. Protect existing footage and avoid impossible changes of geography, identity or time. If exact seamlessness is unverified, provide a proposed transition and its inspection checks rather than guarantee it.
- **Blockout/green-screen:** use supplied coarse choreography as motion/space guidance while rendering the requested materials/style; distinguish coarse from fine tracking. Keep the requested matte/background separation, edge lighting and contact shadows. Verify the actual compositing/conditioning mode rather than treating these words as API switches.

For Seedance-specific task compatibility, cardinality, asset maps and ready templates read [Seedance](seedance.md). For a board-based handoff use [previs](previs.md), which reads actual panels before Stage 2.

## Check and deliver

Every asset must have a role and all requested changes must be localized. Check target model/version, native versus descriptive controls, timing, continuity, exact dialogue/copy and untouched requirements. Deliver one self-contained prompt per independent operation, with a concise upload map when needed. An edit and an extension are separate operations even if the same source clip is used. If a reference is missing/unreadable, finish independent planning and state what blocks the remaining work; never claim to have read it.
