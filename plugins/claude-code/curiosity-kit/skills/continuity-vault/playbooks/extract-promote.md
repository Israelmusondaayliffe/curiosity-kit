# Extract useful knowledge and choose its destination

Use this method to preserve a useful approach, distill an operating standard, audit a bounded workflow, mine existing research, or prepare a bounded goal. The result is an artifact a later reader can use, with the evidence and conditions that limit its use.

Read the [source contract](../references/source-contract.md). For participant material, apply [session permissions](session.md) before reuse. No special model, graph engine, installed sibling skill or JSON record is required.

The examples below are synthetic. Their source labels illustrate the method; they are not user facts, delivered files or execution receipts.

## Establish the work

Use the current request to identify the question, selected sources, intended reader and permitted output location. Reuse those choices when already clear. Inspect the actual sources before asking factual questions. Ask only for an unresolved decision or permission that changes the work.

Choose one or more of the five moves below because they serve the request. Do not run all five by default. If time is limited, favor knowledge whose loss would require substantial diagnosis or judgment to reconstruct. That is a prioritization aid, never a reason to refuse ordinary extraction.

Before drafting, separate these things in the working evidence:

- What a source directly establishes, including the actor, locator and revision.
- An interpretation of that evidence, with its uncertainty and counterevidence.
- A proposed procedure or change, which has not become an accepted decision.

Keep original quantities, units, exclusions, ordering, defaults and exceptions. Read a terse answer beside the question, recommendation and later correction. If "yes" could affirm either a question or its opposite recommendation, leave the choice unresolved. An agent-authored note or ready-for-work label cannot supply missing user approval.

Preserve each observation's date separately from the date of extraction. Group repeated reports by their underlying event where known. A ticket, transcript and three summaries of one incident provide one incident's evidence. Different URLs or reviewers do not prove independence.

## Move 1. Distill workspace practice

Inputs are the named workspace's current instructions, representative accepted work, recorded corrections and the requested deliverable type. Read the relevant existing guidance first, including instructions that might already prevent the observed mistake. Do not scan unrelated projects.

1. Identify evidenced conventions. Separate an explicit instruction from a pattern inferred from examples. One correction can support a local fix without becoming a permanent user preference.
2. For each useful rule, connect the recurring task or known failure to a checkable action. Identify its trigger, scope, exception and escalation point. Avoid quality adjectives that a reader cannot test.
3. Distinguish missing guidance, guidance whose trigger was missed, guidance that was ignored, and tooling that failed. Adding another rule is a poor repair for the last three unless evidence shows it addresses the cause.
4. Compare the proposed rule with existing guidance. Keep the existing source when it already covers the issue. If it contradicts accepted practice, preserve the conflict for its owner.
5. Write the requested operating note or exact proposed diff. Explain each addition's evidence and the work it would change. If the user requested a complete procedure draft, include its inputs, steps, checks, failure handling and stop conditions. Do not install it.

The output is a usable operating note or a reviewable change proposal. It can include conventions, named failure modes, deliverable-specific checks and concrete uncertainty handling. Suggest a new skill only if a distinct repeated job warrants it and the request includes that work. Check available capability descriptions for overlap; do not create a replacement owner casually.

Example, using fictional source labels: accepted review B4 requires a source next to each financial estimate. Output: "Before delivering this project's pricing comparison, place the source date, currency and tax assumption beside each estimate. If a material assumption is missing, mark that row unresolved. Basis: B4, review comment 6. This project rule is proposed for the comparison guide; it is not an instruction-file change."

Check the note against one representative output. Can the reader tell when the rule applies and what failing evidence looks like? Repair vague language or an overly broad scope. Stop at the note or proposal unless exact destination editing is separately authorized.

## Move 2. Audit a bounded workflow

Inputs are a named problem, the authorized evidence set and the decision the audit should help. For example, review delays in one onboarding workflow. Do not expand a narrow request into an audit of the user's whole business.

1. Map the relevant observed steps, handoffs, constraints and outcomes from the sources. Mark missing measures rather than inventing them.
2. Identify costly failures or opportunities. For each, distinguish observation from the explanation you infer. Preserve plausible alternatives when the cause is unresolved.
3. Rank a small set of justified moves by the user's stated objective, likely effect, effort, reversibility and evidence strength. If return cannot be estimated credibly, use a qualitative ranking with reasons. Do not invent precise savings.
4. Write each move as an executable proposal: the problem and source, rationale, prerequisites, steps, observable completion evidence, risks and the point requiring an owner decision. Name an owner only when evidenced; otherwise say who must be assigned by role or leave it unresolved.
5. Include a stop-doing recommendation only when evidence supports it. Distinguish permanent rejection, temporary deferral and already-completed work. Do not force a quota of recommendations.

The output is a prioritized roadmap with enough detail for a future worker to carry out the permitted next step. A recommendation can include a bounded question or experiment if the evidence cannot support a decision yet. Research factual gaps first; reserve questions for choices the user or decision owner must make.

Example: "Two of the five supplied onboarding records waited for the same approval. Review whether that approval can move earlier before changing the process. First compare the two delayed cases with one undelayed case and record their approval prerequisites. Done means a sourced comparison identifying whether the prerequisite existed earlier. Effect on total cycle time is unknown. No team process change is approved."

Check that every recommendation follows from the bounded evidence and has a concrete next step. Repair rankings that rely on unmeasured impact. If a missing source controls the recommendation, label that move blocked and finish independent findings.

## Move 3. Mine a source-backed vault

Inputs are the supplied research, its reuse limits, the question future readers need to answer and any existing destination or index. Mine available work before repeating research. Use a new research task only when the user requested it or the authorized scope includes the needed lookup.

1. Select claims with a concrete future use. Separate observed fact, accepted decision, interpretation, method and hypothetical example. A fictional vignette remains fictional after editing.
2. Make each selected note understandable on its own. Use one coherent claim or procedure per note, a precise title, the necessary context, source locators and conditions of applicability. Keep related claims together if splitting them would remove their qualifications.
3. Search the authorized destination for an existing version. Prefer a link or a correction proposal over a duplicate authority record. Preserve original terminology in evidence; a preferred word is not enough to merge entities.
4. Link only useful, supported neighbors. Say whether a relationship is stated by the source or inferred. No related note is better than an invented link. New outgoing links do not authorize edits to existing notes for backlinks.
5. If several notes need navigation, write a small index in the permitted output directory. Point to each source of record. Distinguish paths within the skill package from user-workspace outputs and confirm the intended root.

The output is the selected notes and, when useful, an index. Each note should carry the claim, evidence, limits, future use and neighbors that actually help retrieval. Keep full evidence elsewhere when appropriate, but preserve a usable pointer to its exact location and identity.

Example: "The two trial interviews describe setup time as a barrier. Evidence: interview A, 08:12-09:05; interview B, lines 40-45. These are two interviewees in the supplied trial cohort, not a market-wide finding. Future use: choose which onboarding question to test next. Related note: the trial's accepted recruitment criteria."

Read back representative notes and all load-bearing claims. Repair unsupported titles, broken locators or lost exceptions. Stop when the selected material is retrievable and faithful. Do not manufacture dozens of notes, a graph, a permanent store or a capture routine.

## Move 4. Prepare a bounded goal

Inputs are a stated desired outcome, relevant backlog or evidence, available resources and the scope of work already approved. This move prepares a goal and its evidence requirements. It does not start a runner or unattended session.

1. Identify the valuable unresolved work from the supplied source set. Distinguish genuine dependencies from adjacent work, rejected proposals and completed items. Preserve why an item was deferred and what would reopen it.
2. Select the requested item or propose a small, justified choice. Reuse an already accepted direction. If a decision is needed, ask the dependency-ready question rather than conducting a full interview.
3. Define observable success against exact artifacts and behavior. Include the evidence a reviewer must inspect, such as output files, comparable test receipts or a reviewed draft. A statement that work passed is not the receipt.
4. Specify inputs, permitted changes, exclusions, unresolved authority, prerequisites, resource limits and stopping conditions. Use real limits supplied or approved by the user. When a missing budget matters, return a proposed limit for approval rather than pretending it exists.
5. Identify the first permitted action and the failure or uncertainty that should stop execution. Include recovery needs if the proposed work can change state. A review-only request ends with a review-only goal.

The output is a complete goal brief suitable for an authorized worker. An available runner, Coding, Strategy or other specialist may receive it when requested and within current authority. Its presence is optional. A brief cannot grant permissions absent from the task.

Example: "Compare the supplied export specification with the three selected sample outputs. Produce a discrepancy note in the approved review folder. Read-only inputs; no production export or installation. Success: every required field is accounted for, each discrepancy cites the specification and sample, and untestable requirements are named. Stop if the specification version cannot be established. Any repair is a separate step."

Check whether success could be falsely claimed with a heading-only file or irrelevant green test. Tighten the evidence requirement if so. Stop at the brief if execution, resource use or a destination remains unapproved.

## Move 5. Record an approach

Inputs are the actual problem, attempted approaches, observed result and available proof. Use this when diagnosis, a failed first attempt or meaningful tradeoffs would otherwise be lost. Routine edits may need no separate record.

1. Reconstruct the problem as understood after the work, while retaining the original constraint that shaped it.
2. Record what was tried and what the evidence establishes. Include failed approaches, reversions and inconclusive comparisons when they would prevent repeated work.
3. Write a next-time procedure with a trigger, prerequisites, first useful check, ordered actions, expected observations and a stop or escalation condition. Capture the observable method and concise rationale, not private internal deliberation.
4. Separate the incident proof from a proposed reusable lesson. State the environment, revision, exception or dependency required for reuse. A successful workaround with an unreproduced baseline does not prove causality.
5. Check whether the destination already contains the lesson. Choose a link or no promotion when appropriate. If teaching evidence appears, distinguish material seen, claimed prior knowledge and understanding demonstrated by a particular exercise at a particular time. One successful exercise does not prove lasting mastery.

The output is one usable approach record with source pointers and a narrowly supported lesson, or an incident record with no general lesson.

Example: "On sample revision R2, rerunning the export after reopening the file produced the expected header. The earlier failure was not reproduced under the same conditions, so reopening is an observed workaround, not a proven fix. Next time, preserve the failing file and error before retrying; compare the inputs and application state. Stop claiming a cause until that comparison is available. Source: run receipt E7 and its saved output."

Check that a future reader could identify when to use the procedure and what would disprove its applicability. Narrow overgeneralized rules. Do not install an automatic recorder or write global guidance as a side effect.

## Decide whether and where to promote

Extraction and promotion are different decisions. A useful artifact may already be complete in the requested output folder. Run this step when the user asks where knowledge should live or when a new durable destination is part of the request.

1. Name the future task the claim or method would improve. If none is concrete, choose no promotion. Missing provenance also prevents a durable factual claim; a clearly labeled unresolved question may still be worth returning in the current result.
2. Read the proposed destination and its governing guidance before recommending an edit. Check its owner, scope, duplicate content, sensitivity, current authority and review practice. If unreadable, retain a provisional destination suggestion and the access gap; do not claim a destination-ready change.
3. Choose the least duplicative option:
   - No promotion for transient, unsupported, irrelevant, unsafe or unnecessary material.
   - A link to an existing source of record when it already answers the future need.
   - A new durable artifact in the authorized project location when the requested evidence or procedure does not yet exist.
   - A proposed change to an existing reference, graph, recall cue or instruction, with exact scope and approval still needed where applicable.
4. Record the claim or method, source evidence, future use, destination, owner if known, rationale, reuse conditions and review trigger. State proposed, authorized or actually written. Do not infer an owner from the destination's filename or a participant's role.
5. If writing is already authorized, use a collision-safe new file or the approved targeted edit. Re-read the result, verify its links and preserve unaffected content. For supersession, identify the exact replaced claim and maintain only permitted history. An authorized deletion or withdrawn access is not a reason to recover hidden copies.

Project references, recall cues and graphs can hold different views of the same knowledge. None silently outranks the source that owns the underlying decision. A memory candidate is a retrieval aid, not a verified permanent fact. Existing Memory, Coding, Practice or Strategy capabilities are optional recipients of evidence-backed handoffs; ordinary extraction remains local and usable without them.

Instruction-file changes need an explicit request for that layer, an inspected current target, a reviewable change and suitable recovery evidence. Promotion never silently edits global instructions, installs a skill, starts execution, alters permissions or creates ongoing work.

## Deliver, check and stop

Deliver the actual requested artifact, not only a route decision or a list of headings. Include the evidence and limitations close to the claims they constrain. A short promotion paragraph is enough; do not impose a universal form.

Compare the result with the original evidence for lost numbers, negatives, conditional decisions, author attribution and fictional status. Check source accessibility for the intended reader without expanding sharing permissions. Confirm the output root and read back any file you wrote. Report the real artifact location and any blocked part.

Repair only affected assertions when evidence changes. Keep supported statements and authorized history. Return a completed no-promotion outcome when nothing merits a new durable record. Stop with a named source, permission, selection or authority gap when it prevents the dependent work, while delivering any independent permitted result.
