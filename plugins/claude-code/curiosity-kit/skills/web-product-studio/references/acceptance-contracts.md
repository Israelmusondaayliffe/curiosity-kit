# Acceptance records and binding contract

Use the existing task record for ordinary work. Read only the named record section needed for the current stage, plus the shared binding interface. These optional JSON records make fragile evidence joins checkable for multi-flow work, a high-visual-stakes gate or a Sites release; a small diagnostic does not need a ledger. The field meanings below are canonical. The helper is not a workflow engine, browser, image decoder, reviewer or authorization service.

## Narrow helper interface

Run `python3 scripts/check_web_evidence.py KIND RECORD.json --root EVIDENCE_ROOT`, where KIND is `route`, `flow`, `visual-contract`, `visual-review` or `sites`. Python 3.9+ and the standard library suffice. The command reads only the record and referenced files, writes nothing and makes no network requests. JSON stdout contains `valid`, `kind`, `errors`, `record_sha256` and `scope: "shape-and-binding-only"`. Exit 0 means structurally consistent current bindings; 1 means validation errors; 2 means unreadable input or command usage. Importable `validate(kind, data, root)` returns a list of error strings.

Every record has `schema_version: 1`, its matching `kind`, a nonempty `task_id`, and `stage: "planned" | "final"`. `planned` means an executable plan, not evidence of execution. `final` means observed records with all required bindings, not automatic product acceptance. A final flow can honestly contain failures; a Sites final record is a release-success record and requires all applicable checks to pass. A final visual contract is a locked target, never a passed image. Read each kind's stricter rules below.

A file binding is `{ "path": "relative/file.ext", "sha256": "64 lowercase hexadecimal characters" }`. Paths are relative to the supplied evidence root, never the process working directory or the containing JSON. Absolute paths, `..`, symlinks escaping the root, nonregular files, missing files, unreadable files and changed bytes fail. Hash ordinary file bytes with SHA-256. Snapshot source into one inspectable archive or a manifest that identifies every relevant source file and its digest; the helper hashes that file only. Inspect the manifest's completeness and current checkout/build correspondence separately. Never say a manifest hash verifies every listed file by itself. Preserve old snapshots rather than rewriting prior accepted evidence.

A build is `{ "id": "unique-rendered-build", "source": BINDING, "fixture": BINDING, "origin": "http://127.0.0.1:PORT" }`. The source snapshot and fixture describe what actually ran. Origin must be an HTTP(S) origin without credentials, path, query or fragment. Build IDs are labels joined to capture receipts, not proof of server identity. Read the running app marker, process/session ownership and actual build receipt before attributing a capture. A reviewed source hash cannot attest a stale server.

Viewports are objects with unique `id`, positive integer `width` and `height`, plus `framing` for visual contracts. A state is a unique nonempty string. A capture is `{ "id", "viewport_id", "state_id", "build_id", "artifact": BINDING, "receipt": BINDING }`. Its receipt is JSON containing the exact `task_id`, `build_id`, `source_sha256`, `fixture_sha256`, `origin`, `viewport: {id,width,height}`, `state_id`, `artifact_sha256`, `capture_tool` and `captured_at`. The helper joins these values. It does not establish that the tool actually emitted the receipt, that an image decodes, or that the claimed state appears. Retain genuine host/browser receipts and open the artifact with an available image/video viewer; do not invent receipts to satisfy the schema.

An inspection is `{ "artifact_sha256", "inspector_id", "result": "viewed" | "unviewable", "receipt": BINDING }`. It records an actual decode/view operation and its host result. The helper requires matching inspected hashes for passing visual records but cannot authenticate the receipt or visual judgment. A fake PNG header remains unviewable until a real decoder/viewer succeeds; a hash match is no repair.

## Route record

Fields: `route`, `objective`, `rationale`, `design_constitution` (one string or null), `visual_stakes` (`ordinary` or `high`), `visual_gate_required` (boolean), `acceptance_flow` (binding), `visual_contract` (binding or null), `sites_record` (binding or null). Routes are `greenfield`, `redesign`, `reference-to-code`, `design`, `image-first`, `targeted-fix`, `diagnosis`, `quality-assurance`, `sites-artifact`.

`design` covers design/image-only output; `image-first` is a retained legacy route spelling whose objective must state whether the output is a comp or working implementation. The optional `design_selection` object holds `selected` (matching `design_constitution`), nonempty `evidence` strings, `rationale`, and `rejected: [{name,reason}]`. Selection checks preserve evidence and rationale; old donor constitution names are labels, not a mandatory installed allowlist.

The helper validates joined record kinds and matching task IDs. High stakes requires the visual gate; an explicit required gate requires a contract even when the stakes label is ordinary. A Sites route requires the Sites record. One selected constitution never overrides supplied or approved visual authority. The helper does not infer stakes from keywords: “remove the 3D animation” is not permission to create a new high-stakes build. A planned route can point to planned documents; final joins must point to final records. Use notes instead if no JSON route is useful.

## Flow record

Use `assets/acceptance-flow.json` as a clearly planned example. Fields: `build` (null until executed), `viewports`, `states`, `flows`. Each flow has unique `id`, `name`, `actor`, `goal`, `preconditions` (string list), `critical` (boolean), `recovery_flow_id` (another flow ID for each critical flow), `status` (`unrun`, `passed`, `failed`, `blocked`), and nonempty ordered `steps`.

Each step has a unique `id` within its flow, `action`, `expected`, `evidence_plan`, `viewport_id`, `state_id`, `status`, `observation` (null until observed), and `evidence` (list of bindings). Use one action per step and literal expected values or a defined comparison oracle. Expected and observed are separate. The helper rejects missing recovery joins, missing viewport/state joins and duplicate IDs. Planned flows and steps stay unrun with no observation/evidence. A final record requires a real build, observations/evidence for passed or failed steps, and a reason in `observation` for blocked steps. A passed flow requires every step passed. Failed/blocked/unrun cases cannot silently become a passing flow. A critical recovery flow is a genuine failure/recovery case, not a pointer to the same happy path.

For rendered behavior, evidence must include real browser actions and fresh resulting observations. For durable writes include independent source-owned readback, reload and a second consumer when required. The helper checks files and joins; it does not read arbitrary transcripts as proof of outcomes or certify that a recovery case is meaningful.

## High-stakes visual contract

Load this section only when picture fidelity is load-bearing or explicitly requested. The five method stages are target-locked → hero-spike → visual-passed → full-build → final-reviewed. “Hero-spike” means the smallest representative high-risk surface; it need not be a marketing hero. The checker records the two review moments rather than manufacturing five redundant workflow documents.

Fields: `objective`, `first_glance`, `proof_slice`, `author_ids`, `builder_ids`, `references`, `traits`, `forbidden`, `viewports`, `states`, `required_views`, `medium`, `constraint_conflicts`, `conflicts_resolved`, `secondary_features_started: false`, `visual_gate: "unrun"`, `incomplete_wording`.

- References: a task-appropriate nonempty list of objects `{id,source,permission_status,artifact,inspection}`. Permissions are `owned`, `licensed`, `supplied-by-user` or `public-reference`; reference permission is not permission to redistribute. Final locked contracts require actual artifact and successful inspection bindings; planned contracts allow nulls.
- Keep nonempty `traits` and `forbidden` lists with every distinct critical requirement. The example uses three of each; merge genuinely overlapping wording, but do not pad a small brief or discard a fourth load-bearing requirement to fit a count. Reference count follows accepted evidence needs, not a cap.
- Required views: unique `{id,viewport_id,state_id,reference_ids,proof_slice}` entries. `proof_slice` is boolean; at least one true view is required. List every material final view/state, including mobile crop when framing changes and default/extreme states when applicable. Final review covers all; initial visual pass covers the true subset. Explain omitted dimensions in the brief rather than assuming every Cartesian combination matters.
- `medium` has `selected`, `rationale`, nonempty `rejected` alternatives and an observable `switch_condition`. `constraint_conflicts` is a list; no locked contract may retain unresolved conflicts. Resolve actual physical/product conflicts, not a hardcoded keyword pair.
- Author/build identities are real host/person identities known to the task owner. They are mandatory inputs. A boolean alone is not independence.

## Visual review record

Fields: `state` (`visual-passed` or `final-reviewed`), `contract` (binding), `build`, `reviewer: {id, independent, receipt}`, `captures`, `inspections`, `comparisons`, `score`, `differences`, `visual_gate`, `functional_gate`, `flow`, `decision`, `incomplete_wording`, `previous_review`, `full_build_receipt`, `secondary_features_started_before_visual_pass`.

Planned examples have null bindings/build/reviewer receipt/score, empty captures/inspections/comparisons/differences, gates `unrun`, decision `incomplete`, false early features, and honest incomplete wording. They cannot contain a pass. Final reviews require a fully validated final contract, bound build, reviewer receipt, captures and successful inspections of every used reference/render. Reviewer ID must differ from every builder and author, and `independent` must be true. Inspect the actual host assignment/report to establish independence; the helper can only compare supplied IDs and validate receipt bytes.

Each comparison is `{view_id,capture_id,reference_ids,observation}`. IDs resolve exactly to the contract view and capture; reference IDs must equal the view's accepted list, not substitute a new reference. Capture viewport/state/build/source/fixture/origin must match the frozen conditions and receipt. One comparison per required view; no unrequested or duplicate views. Artifact receipt and inspection bindings remain separate because capture is not inspection.

Differences are `{view_id,severity,description,contract_trait}`. `contract_trait` identifies a load-bearing trait or is null for non-contract polish. Severity meanings and score bands live in `playbooks/verify.md`; no score can average away P0–P2. Final reviews use gates `passed`, `failed` or `blocked` (functional may be `unrun` until final completion), scores 0–10, and decisions `proceed`, `complete`, `repair`, `method-switch`, `incomplete`. A visual pass requires score ≥7, no P0–P2 difference, and no early secondary feature work. Otherwise choose repair, method-switch or incomplete and give honest wording.

At `visual-passed`, `previous_review` and `full_build_receipt` are null; the bound contract and captured proof slice establish target-lock and spike evidence. At `final-reviewed`, `previous_review` binds the actual prior final-stage `visual-passed` record with a passed visual gate and proceed decision. Its contract and task must match. `full_build_receipt` is bound JSON with `task_id`, current `build_id`, `source_sha256`, `fixture_sha256`, exact `prior_review_sha256`, and `stage: "full-build"`. It records that full build followed the accepted spike. The checker rejects missing links, cycles and substituted contracts; the task owner checks real chronology/host receipts. Changes to an accepted target require a new lock and initial visual pass. Current full-build source can differ from the preserved spike source.

A `complete` decision is valid only at final-reviewed with passed visual and functional gates, a bound final flow whose build equals the current review build, and all flows passed. A visual-passed spike never completes the product. If no independent reviewer is available, report the gap; do not mint a different ID for the builder.

## Sites grouped record

`assets/sites-records.json` is a planned example. The six canonical groups are `brief`, `sources`, `curation`, `authority`, `profile`, `release`; their product/teaching decisions are in `playbooks/sites-artifact.md`. Keep these in one record rather than duplicating flows or visual gates.

Source IDs must be unique. Brief content IDs, curation decisions, authority references and public allowlist entries resolve to actual source records. Each selected authority/public source has a selected curation decision. Final used sources must be inspected with bound evidence. An exact prompt has exact text, parameters and original evidence; do not convert inferred workflow into an original prompt. Public export eligibility requires `allowed`, inspected, selected, and an explicit `public_projection`. The projection contains only approved public fields; private locators, account identifiers and private prompt text do not become exportable because the source was useful for research. The helper checks joins/labels; a real privacy inspection judges the actual export.

The supported `brief.job` values are teaching-reference, portfolio, interactive-report, review-workspace, project-board, dashboard, planner, tracker, action-tracker, calculator, scenario-planner, gallery, registry, catalog, portal, hub, knowledge-system, operational-playbook, prototype, simulation, game, workflow-app and lightweight-tool. Choose the actual closest job; extend this vocabulary deliberately with schema and tests if a materially different job is required.

`profile.required` and `profile.checks` may both be empty for an ordinary private artifact with no applicable special profile. Teaching-reference requires teaching-library. Public delivery researched with nonpublic sources requires public-source-privacy. Declared profiles require every named check from the Sites playbook; do not create irrelevant checks merely to fill a list.

Planned records describe a content spine, source/curation work, selected or pending direction, planned profile checks and requested delivery. Build/deployment/health/anonymous checks stay unrun or not-required. No successful deployment or retrospective is required to start. Final release records require current source/build, passed build evidence, a final passed flow joined to that source/build, passed profile checks, independent review evidence, and a real retrospective. Deployment is conditional on the requested delivery; a completed local artifact requires no fabricated Sites URL. When deployment is requested, require exact version, succeeded deployment receipt, verified URL and a separate passing health observation. Public delivery additionally requires an anonymous access test, explicit public source allowlist and privacy-scan evidence. Platform deployment success alone does not establish live health or access.

Final deployment receipt JSON contains exact `task_id`, `build_id`, `source_sha256`, `version`, `deployed_url`, and `status: "succeeded"`. The health observation receipt has the same identity and `status: "passed"`. The anonymous-access receipt has `task_id`, `build_id`, `source_sha256`, `audience`, `status: "passed"`, and also version/deployed_url when deployed. The helper cross-checks these bindings against the released build and declared destination. Genuine provider/browser output must substantiate the notes; hand-filled JSON does not prove a deployment or anonymous visit. Local final records use deployment `not-requested`, health `not-required`, and null receipts. Unneeded anonymous checks use `not-required` and null evidence.

## Evidence limits and migration

Schema validity, current bytes, genuine capture, image decoding, independent judgment, accepted functional outcomes and authorized delivery are different claims. The checker establishes only the first two and internal joins; `verify.md` owns the remaining checks. Unsupported tools or unavailable evidence remain blocked/unrun, never replaced with permissive flags.

The original high-stakes gate capped references at three and required exactly three traits/failures. This is deliberately adapted to task-appropriate nonempty lists: preserve the source-bound method and every critical requirement without padding or truncating the accepted brief.

Migrate old `priority/gap` to `severity/description` by meaning. A material failure in an accepted secondary state is blocking even if called “secondary”; a harmless non-contract optical preference is P3. Old `visual-incomplete` becomes `incomplete`. Old `untested` becomes `unrun`. Do not mechanically promote a historic hash or `independent: true` into a current final record. Preserve the old receipt as history, capture/inspect/review the exact candidate, and write the new record only from those observations.
