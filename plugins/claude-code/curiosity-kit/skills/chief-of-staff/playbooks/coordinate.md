# Coordinate a useful result

The [entry's authority contract](../SKILL.md#authority-lives-here) applies throughout. Read [host contract](../references/host-contract.md) before selecting a tool or making a host claim. This method owns integration; it does not replace a specialist's implementation or a selected engine's state machine.

## 1. Establish what would finish the request

From the request and settled context, identify the user's outcome, requested artifacts/actions, intended audience, non-negotiable constraints and observable finish. Separate facts from choices and assumptions. Keep task deadlines, event times and completion timestamps distinct; leave unknown deadlines unset and label suggested work dates as proposed. Keep a short working brief only when it prevents loss; use an existing task record if adequate. A one-line edit does not need a project document.

Distinguish the requested mode: explain, recommend, plan, inspect, draft, implement, verify or deliver. An unchanged noun with a different verb can require different authority and proof. Preserve every requested deliverable and the user's own edits. If the user names two incompatible controllers, inspect their contracts and obtain the necessary owner choice rather than nesting them.

Investigate observable facts yourself through authorized sources. Ask about decisions only when the answer changes the result, scope, cost, route or commitment. State a defensible assumption for a small reversible ambiguity; do not assume a consequential permission. An empty question list with missing prerequisites is blocked understanding, not completed discovery.

## 2. Select the smallest sufficient owner

Consult the [capability map](../references/capabilities.md), then actual current discovery. Choose by outcome and method contract, not keyword count, prestige, available worker slots or the number of verbs. A research memo may need one research owner. A web product can remain Web-owned. Use several specialists when their distinct expertise contributes something essential.

Read the selected method in full and its conditional resources. Check its inputs, output, prerequisites, local activation rules and stopping condition. Do not recommend skipping a named method based only on its title. A requested unavailable method remains unavailable; offer an equivalent authorized alternative only if it actually meets the same requirement, and disclose a material method change.

The map is not an installation manifest. Reconcile exact identities, aliases, source versus installed copies and resource availability. Candidate, accepted, installed, discoverable and successfully exercised are different facts. Do not treat missing discovery as proof that no source exists or that installation is authorized.

## 3. Choose sequence and practical effort

Identify real dependencies. A draft can begin from settled facts while another reader verifies an independent claim; final delivery waits for that claim if essential. Shared-file integration and dependent decisions need ordering. Independent source reads or disjoint artifacts may run together. Neither “everything in parallel” nor “one by one” is a universal rule.

Use available suitable workers and tools, honoring explicit user/model/context choices. If an exact required selection is unavailable, report the affected launch rather than silently substitute. With no exact selection, choose sufficient capability for the work: routine extraction may need less effort than a difficult repair or integrated review. Use observed/reported budget honestly; distinguish money, messages, time and tokens. A plan's model name does not prove billing or remaining usage.

Bring a consequential trade-off to the hands-on user with the recommended option, its practical consequence and what decision is needed. Do not interrupt over every internal step. Do not manufacture a resource forecast or battery reading. Local-computer work can stop when the computer sleeps even when the conversation runs in the cloud; inspect actual execution location before promising continuity.

Review should target the actual risk and requested bar. Use an independent reviewer when the method or consequential judgment requires one; self-review is not independent. One integrated final critic is often better than many overlapping panels. Keep demonstrated baseline checks, and repeat only what changed or what remains necessary. A count of reviewers or passing checks is not quality.

## 4. Assign work with a complete local contract

For direct work, execute the chosen method. For a fresh worker, give the minimum complete [handoff](../assets/work-handoff.md): exact task and scope; current inputs and versions; relevant decisions; selected full method and available resources; authorized operations and denials; owned outputs including temporary work; budget/stop; expected artifact, checks and return. Pass actual data needed for the task, not the whole private conversation or plan.

Do not give two writers the same file or effect. If actual tools support nested work and it helps, preserve remaining resource/depth constraints and prevent ancestor-return cycles. Do not invent unavailable delegation tools. Invoking a method in the current context is not a fresh independent worker.

Use the selected engine's own packet/return schema where required. For Operating Graph, for example, copy the actual identities, digest, owned paths, artifact versus evidence distinction and criterion-evaluator requirements into the worker brief; supply observed host-only launch/completion IDs from the controller. Never substitute this generic handoff for a required typed contract. Workers must not fabricate host receipts.

Confirm the launch actually happened. Retain its returned identity and owned resources if needed for recovery. Report useful progress, decisions and blockers; avoid narrating each internal operation. A running child is not a failed child just because its transcript has not yet been collected.

## 5. Integrate returns and recover narrowly

Inspect the returned artifact, then its relevant checks. Does it answer the original question or merely propose how to answer it? Are source claims linked and uncertainty carried? Does a check bind to the actual consumed version? Does another artifact depend on a stale draft? Are required side effects observed or only attempted?

If an artifact is missing, request the concrete missing return or locate it through the actual authorized output. Do not promote its dependents from a “done” label. A failed worker blocks its dependents, not unrelated ready work. A stopped reader leaves coverage missing. Observe actual child start/end windows before claiming work was serialized or parallel.

Repair the smallest required defect at its canonical owner, with one writer. Keep the failing artifact/result intact where useful. Change the approach when a repeated failure brings no new evidence. Do not erase attempts, reset a selected engine's cap, weaken the user's bar or call a later parent correction a passing native run. If the required next step exceeds authority or resource limits, report the exact unresolved result and choice.

For interruptions, uncertain effects or a resumed task, use [Resume](resume.md). Do not roll back a remote effect by merely restoring a local file.

## 6. Finish the whole result

Compare every original deliverable and essential criterion with the final artifact and applicable proof. Check cross-artifact names, facts, audience, links, ownership and versions. A good contribution may still form a bad combined result. Resolve contradictory sources rather than picking the first one that supports the draft.

Read back the saved output where persistence matters. Check exact requested destination and usable links. Distinguish local file creation, private remote delivery, installation, publication and actual external effect. If a destination operation is uncertain, stop replay and reconcile it first. Do not say “sent,” “installed,” “accepted” or “published” from an authored receipt or upload attempt alone.

Return the useful result concisely. Say what is complete, the material limit and the next necessary action. Do not drown the user in workflow labels. If all essential work is complete, finish; optional improvements do not keep the task artificially open.

## Examples

A request for a report and a short announcement may be one writing/research owner producing both, with source checks before final integration. A request for a working page plus a model-specific image prompt may need Web and Visual, with dimensions and factual claims agreed between them. Neither implies paid generation, publication or an independent review fleet. If the user requests only a route recommendation, explain the selected route and stop there.
