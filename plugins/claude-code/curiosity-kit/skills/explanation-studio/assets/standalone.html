An illustrative explanation

No reply does not mean no change.

A timeout tells the client that it did not receive a response in time. It does not tell the client whether the service saved the change.

Check the retry rule before repeating the request.

In this example, the client may retry only when retry_safe is true. If the flag is false, the rule does not permit a retry. The first write's result is still unknown.

This is a teaching example. It does not establish whether a real application's writes are safe to repeat.

Show the technical distinction

The client observes a timeout. That observation concerns the response deadline, not a confirmed transaction outcome.

A real service may use an operation identifier, deduplication or a status check to resolve uncertainty. None of those capabilities is assumed here. Inspect the service's actual contract before choosing a recovery action.

Keep the missing reply separate from the completed work.

After the response deadline, report what you know: no reply arrived in time. Do not report “the write failed” unless another source establishes that fact.
